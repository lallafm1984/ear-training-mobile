# 선율·2성부 화면 깜박임 수정 및 빌드 62 무선 설치·AAB

## 원인과 변경

`NotationPracticeScreen`의 최초 생성 effect는 `generate`에 의존하고,
`generate`는 `useNoteInput.reset`에 의존했다. 기존 `reset`은 생성된 악보의
첫 음에 의존하므로 새 악보를 설정할 때마다 콜백이 바뀌었다. 그 결과
500ms 간격으로 악보를 다시 생성하며 로딩 화면과 악보 화면이 반복됐다.

- `reset`이 새 첫 음·마디 수·마디 길이·성부 조건을 필수 인자로 받아 현재 악보에 의존하지 않게 수정했다.
- 새로운 생성 요청, 설정 변경, 화면 종료 시 대기 중인 생성 타이머를 취소한다.
- 악보 생성과 답안 입력·연습 기록 저장의 기존 로컬 처리 방식을 유지한다.

## 검증

- 수정 전 화면 회귀 테스트에서 선율과 2성부 모두 4초 동안 8회 생성되는 현상을 재현했다.
- 수정 후 화면 회귀 테스트 10개 통과: 실제 생성기를 사용한 네 카테고리 진입,
  선율·2성부의 입력 유지·제출·다음 문제, 모의시험, 생성 취소, StrictMode 중복 방지.
- 전체 Jest 18개 스위트, 269개 테스트 통과.
- TypeScript, ESLint, 변경 파일 Prettier 검사 및 Android Hermes 번들 생성 통과.
- 영문 임시 프로젝트에서 Expo prebuild 후 로컬 Gradle `:app:assembleRelease` 성공.
- SM-S931N에서 선율 진입, E4 입력 및 대기 후 악보·커서 유지 확인.
- 같은 기기에서 2성부 진입, 높은음자리 E4·낮은음자리 C3 입력 및 대기 후 유지 확인.
- 확인한 앱 프로세스 로그에 `FATAL EXCEPTION` 및 `ReactNativeJS` 오류 없음.
- 실제 기기에서는 테스트 답안을 제출하지 않았다. 마지막 화면의 테스트 입력은 초기화했다.

## 추가 원인 분석: 언제, 왜 발생했는가

**8월 22일 16:48:09(KST), 프로덕션 빌드 전 Codex가 React 훅 의존성 경고를 정리하면서 만든 회귀 오류다.**
보관된 릴리스 파일을 대조하면 이 변경은 빌드 60부터 포함됐으며, 61에도 그대로 남아 있었다.
고객의 정확한 설치 버전과 업데이트 날짜는 확인하지 않았으므로 고객별 발현 날짜까지 단정하지 않는다.

### 발생 변경의 근거

- Git HEAD `e5858fe`(2026-06-29)의 `generate`는 6개 조건에 의존했으며 `reset`을 포함하지 않았다.
- 8월 22일 작업 원문에서 `selectInputNote`, `resetNoteInput`을 추출하고 두 함수를 `generate` 의존성 배열에 추가한 패치를 확인했다.
- 원문 시각은 `2026-08-22T07:48:09.279Z`이며 한국 시각으로 16:48:09다.
- 해당 작업은 `react-hooks/exhaustive-deps` 경고를 제거하는 과정이었다. 함수의 의존성이 바뀌면 화면 초기화 effect의 재실행 조건도 바뀐다는 점을 놓쳤다.
- 당시 변경은 현재 Git HEAD 뒤의 미커밋 작업에 들어 있다. 따라서 특정 Git 커밋이 문제를 도입했다고 지목하지 않는다.

원문 위치: Codex 작업 `01a027ed-1f0b-7c92-9f73-ec1f984841d6`의 1791번째 JSONL 레코드.
원인 파일에 해당하는 패치만 `build/notation-fix-v62-qa/root-cause/20260822-164809-notation-dependency.patch`에 보관했다.

### 실제 릴리스 파일 대조

각 AAB/APK의 `index.android.bundle`을 추출하고 같은 Hermes 도구로 디스어셈블해
화면의 최초 생성 콜백과 입력 훅의 `reset` 콜백을 확인했다.

| 빌드 | `generate` 의존성 | `reset` 의존성 | 이번 오류와 관련된 구조 |
| ---- | ---------------- | ------------- | ----------------------- |
| 58 | 6개, `reset` 미포함 | 첫 음 등 4개 | 생성 결과가 최초 생성 effect를 재실행하지 않음 |
| 59 | 6개, `reset` 미포함 | 첫 음 등 4개 | 위와 동일 |
| 60 | 8개, `reset` 포함 | 첫 음 등 4개 | 생성 결과가 다음 생성을 촉발하는 순환 발생 |

| 62 | 8개, `reset` 포함 | 없음, 새 조건을 필수 인자로 전달 | 콜백을 안정화해 순환 차단 |

설치 전 휴대폰에서 추출한 v61 APK의 JavaScript 번들 SHA-256은 보관된 v61 AAB의 번들과 일치했다.
따라서 이번에 확인한 휴대폰 증상을 개발 소스에만 존재하는 문제로 볼 수 없다.
이 표는 해당 생성 루프의 구조를 비교한 것이며 구버전 전체 기능의 무결성을 보증하지는 않는다.

### 왜 선율과 2성부에서 계속 깜박였는가

두 카테고리는 `shouldUseFirstNoteHint`가 참이어서 생성한 악보의 첫 음을 입력 훅에 전달한다.
새 악보의 첫 음은 같은 음높이여도 새로운 객체다. 기존 `reset`은 그 객체에 의존했으므로
악보가 바뀔 때마다 새로운 함수가 됐다. `useCallback`을 썼다는 사실만으로 함수가 항상 고정되는 것은 아니다.

```text
새 악보 생성 → setScore → 첫 음 객체 변경 → reset 함수 변경
    → generate 함수 변경 → useEffect([generate]) 재실행
    → 로딩 표시 및 500ms 뒤 새 악보 생성 → 반복
```

리듬은 첫 음 힌트를 쓰지 않아 같은 지속적인 반복이 없었다.
마디 받아쓰기도 첫 음은 고정된 null이지만, 초기 기본 마디 수 4가 실제 1마디로 바뀌면서
한 차례 불필요한 재생성이 일어나는 경우가 격리 실험에서 확인됐다. 빌드 62 수정은 이 중복도 방지한다.

반복은 예외를 던지거나 즉시 재귀 호출하는 방식이 아니라 500ms 타이머마다 일어난다.
따라서 앱 프로세스가 살아 있고 충돌 로그가 비어 있어도 연습 화면은 사용할 수 없다.
문제 생성마다 실행 집계 콜백도 호출되므로 해당 세션의 실행 횟수가 과대 집계될 수 있다.
일반 연습 기록의 `addRecord`는 제출·평가 경로에 있어 이 반복 자체가 채점 기록을 계속 저장하지는 않는다.

### 원인만 바꾸는 격리 실험

현재 앱 소스나 설치 앱을 되돌리지 않고 별도 테스트 복사본에서 비교했다.
React·악보 생성기·테스트 입력·타이머 취소 처리는 공통으로 유지하고,
생성 의존성 추가 여부와 `reset` 안정화 여부만 바꿨다. 매 500ms마다 React 갱신을 완료한 뒤 총 4초를 관찰했다.

| 실험 조건 | 선율 생성 횟수 | 2성부 생성 횟수 | 리듬 | 마디 받아쓰기 |
| --------- | -------------- | --------------- | ---- | ------------- |
| A: 의존성 추가 전 구조 | 1 | 1 | 1 | 1 |
| B: 의존성 추가 + 기존 `reset` | 8 | 8 | 1 | 2 |
| C: 의존성 추가 + 빌드 62의 안정된 `reset` | 1 | 1 | 1 | 1 |

같은 환경에서 B만 재현되므로 문제의 직접 원인을 네트워크나 계정 상태 변화로 설명할 필요가 없다.
실험 JSON, 릴리스별 번들 해시, 디스어셈블 발췌는 `build/notation-fix-v62-qa/root-cause/`에 보관한다.

### 왜 출시 전 검증에서 놓쳤는가

- 당시 자동 테스트는 악보 생성·채점·인증·공지 등 개별 로직을 검증했다. 실제 `NotationPracticeScreen`과 입력 훅을 함께 마운트하고 대기하는 테스트가 없었다.
- ESLint는 필요한 의존성의 누락을 검사하지만, 그 의존성 연결이 업무 흐름의 순환을 만드는지까지 보장하지 않는다. 경고 0건을 기능 정상의 근거로 확대해 판단한 것이 잘못이었다.
- 기록에 남은 실기기 확인은 로그인 유지·전면 실행·원격 공지와 업데이트 흐름 중심이다. 선율·2성부 진입 및 대기까지 확인했다는 증거는 없다.
- 여러 변경과 릴리스가 미커밋 상태로 이어져 Git만으로 문제 도입 시점을 바로 찾을 수 없었다. 이번에는 작업 원문과 실제 릴리스 번들을 추가 대조해야 했다.

### 재발 방지

이미 적용한 조치는 안정된 `reset`, 대기 중 생성 취소, 화면 회귀 테스트 10개와 실제 휴대폰의 선율·2성부 입력 확인이다.
의존성 경고를 숨기거나 의존성을 다시 누락시키는 방식으로 수정하지 않았다.

다음 출시부터는 훅 의존성 수정도 동작 변경으로 검토하고,
수정된 화면을 직접 열어 대기·입력·제출·다음 문제까지 확인한 결과를 빌드 성공과 구분해 남겨야 한다.
릴리스별 소스 커밋과 산출물 SHA-256도 함께 고정하면 회귀 추적이 쉬워진다.
이 분석 중 추가 앱 수정·새 빌드·서버 변경·스토어 배포는 하지 않았다.
